ข้อมูลตัวละคร

เซิร์ฟเวอร์จะพยายามโหลดข้อมูลตัวละครจาก Honkai: Star Rail API เมื่อเริ่มทำงาน:

  • API หลัก: honkai-starrail-api.vercel.app/api/v1/characters
  • เซิร์ฟเวอร์แปลงข้อมูลที่ได้รับเป็น ID, ชื่อ, ระดับดาว, สาย (Path), ธาตุ (Element) และ URL รูปภาพ ก่อนเก็บไว้ในหน่วยความจำเพื่อให้หน้าเว็บเรียกใช้
  • หากเรียก API ไม่สำเร็จ จะใช้ข้อมูลสำรองจาก characters.json ที่อยู่ในโฟลเดอร์หลักของโปรเจกต์

รูปภาพตัวละคร

หน้า Characters ใช้ URL รูปภาพที่มากับข้อมูลตัวละครจาก API (ช่อง icon หรือ image) หรือจาก characters.json เมื่อใช้ข้อมูลสำรอง รูปภาพจึงอาจถูกโหลดจากเซิร์ฟเวอร์ภายนอกตาม URL ของแต่ละรายการ

ข้อมูลคิวและประวัติ

หน้า Teams ใช้จัดทีมตัวละครได้ 4 ช่อง และใส่ Relic ได้ 6 ช่องใต้ตัวละครแต่ละตัว ได้แก่ Head, Hands, Body, Feet, Link Rope และ Planar Sphere โดยเลือกจากแผงด้านล่างหรือจับลากไปวาง Relic ต้องตรงกับประเภทช่องและเลือกซ้ำไม่ได้ มีสถานะกำลังโหลด, ว่าง, สำเร็จ และผิดพลาด พร้อมปุ่มลองใหม่เมื่อโหลดข้อมูลไม่สำเร็จ ทีมและประวัติการเปลี่ยนทีมเก็บไว้ในหน่วยความจำของเซิร์ฟเวอร์ ข้อมูลจะเริ่มใหม่เมื่อเซิร์ฟเวอร์ปิดหรือเริ่มทำงานอีกครั้ง

  • GET /team อ่านทีม และ PUT /team บันทึกตัวละคร 4 ช่อง โดยส่ง {"ids":["id-1",null,"id-3",null]}; หนึ่งทีมเลือกตัวละครซ้ำไม่ได้
  • หน้า Characters แสดงคิวตามลำดับ FIFO: GET /watchlist อ่านคิว, POST /watchlist เพิ่มตัวละคร และ DELETE /watchlist/process ประมวลผลตัวถัดไป พร้อมสถานะกำลังโหลด, คิวว่าง, สำเร็จ และผิดพลาด
  • /history อ่านประวัติ และ POST /undo ย้อนการกระทำล่าสุด
  • /characters?sort=selection อ่านรายการตัวละครที่เรียงแล้ว โดยเลือกอัลกอริทึมได้เป็น selection, insertion หรือ bubble

Graph และประสิทธิภาพของ DSA

หน้า Characters เป็น JavaScript ฝั่งเบราว์เซอร์ (โปรเจกต์นี้ไม่ได้ใช้ React) ส่วนการโหลดและตรวจสอบข้อมูล รวมถึง Queue/Stack อยู่ฝั่ง Express ใน server.js และกราฟ UI อยู่ใน public/dashboard-experience.js

  • Graph: สร้างกราฟสองฝั่งจากตัวละครและโหนดคุณลักษณะ Path/Element โดยเชื่อมตัวละครกับคุณลักษณะที่มีในข้อมูลจริง จากตัวละครที่เปิดรายละเอียดใช้ BFS ไม่เกิน 2 ระดับเพื่อค้นตัวละครที่มี Path หรือธาตุตรงกัน แล้วให้เปิดดูต่อได้ กราฟมี V โหนดและ E เส้นเชื่อม; สร้างกราฟและ BFS ใช้ O(V+E) เวลาและ O(V+E) หน่วยความจำ โดย BFS จำกัดที่ความสัมพันธ์ตรงเพื่อไม่แสดงความเชื่อมโยงทางอ้อมเป็นความเหมือนโดยตรง
  • Queue: ใช้ doubly linked list ใน Express ทำ enqueue, dequeue และคืนรายการไปหัวคิวเมื่อ undo ได้ O(1); ก่อนหน้าใช้ array shift()/unshift() ซึ่งต้องเลื่อนสมาชิก O(n) การแสดงคิวยังคงใช้ O(n) ตามจำนวนรายการ
  • Stack: เก็บประวัติการแก้ไขทีม/คิวด้วย push/pop ซึ่งเฉลี่ย O(1); แสดงประวัติกลับลำดับใช้ O(n)
  • Map/Set: ฝั่ง Express ใช้ Map จัดทำดัชนี Relic ตาม ID (สร้าง O(n), ค้นหาเฉลี่ย O(1)) และ Set ตรวจ ID ซ้ำ (O(n) โดยเฉลี่ยทั้งชุด) ช่วยให้ตรวจคำขอบันทึกทีมได้โดยไม่ค้น catalog ซ้ำทีละรายการ
  • Sorting/Filtering: อัลกอริทึม Selection, Insertion และ Bubble ใน Express มีเวลา O(n²); การกรองข้อมูลที่โหลดแล้วบน browser ใช้ O(n) ต่อการเปลี่ยนตัวกรอง และการเรียง Relic ใช้ O(r log r)

หน้าหลักและหน้าเลือกทีม/Relic แสดง loading, empty, error และ success ตามสถานะการโหลดหรือการบันทึก พร้อม retry เมื่อโหลดล้มเหลว เพื่อให้ผู้ใช้ทราบผลและทำต่อได้โดยไม่ต้อง reload หน้า

ข้อมูล Relic

หน้า Relic แสดงรายการพร้อมชื่อ ตำแหน่ง ระดับดาว รูปภาพ รายละเอียด และโบนัสเซ็ต โดยอ่านข้อมูลจาก cache ของ starrail.js ผ่าน GET /relics ซึ่งส่งจำนวนรายการและข้อมูลในฟิลด์ data
